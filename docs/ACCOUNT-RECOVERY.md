## 2. Кому принадлежит аккаунт: выбранная основа проекта решения

Для первого recovery-процесса выбираем **заранее подтверждённый адрес этого аккаунта**. Не добавляем вход через Discord, секретные вопросы, ручной сброс по нику/скриншоту, новый сервис авторизации или слияние аккаунтов.

| Состояние | Проектируемое действие |
|---|---|
| Есть действующая сессия и известен пароль, почта ещё не связана | Подтвердить текущий пароль, отправить challenge на сохранённый адрес, затем явно подтвердить его с доказательством доступа к ящику и повторной аутентификацией того же аккаунта. |
| Пароль забыт, ранее подтверждённый адрес совпадает с текущим | Выдать короткоживущий reset challenge через этот канал; только его успешное применение меняет пароль. |
| Пароль забыт, email никогда надёжно не подтверждался | Не отправлять право на сброс на произвольно записанный адрес; публично показывать тот же нейтральный результат запроса. Это неподдержанный случай, не «успешное восстановление». |
| Потеряна также почта либо нет другого ранее подтверждённого фактора | Автоматический перенос доступа не разрешён. Поддержка не получает скрытой кнопки сброса без доказательства. Возможная альтернативная процедура требует отдельной модели угроз и решения до обещания пользователям. |
| В старой записи уже стоит `emailVerified: true` | Не превращать флаг автоматически в новое доказательство. Нужны проверенное происхождение либо повторная привязка с известным паролем. |
| Аккаунт требует MFA или имеет особые ограничения | Email reset не снимает эти требования и не создаёт обход. Покрытие привилегированных/MFA-аккаунтов нужно принять отдельно до включения для них. |

Возможный риск старой модели: человек ошибся в адресе, но уже создал приватные данные. Автоматический reset по такому адресу отдаст право смены пароля владельцу другого ящика. Это модель угроз, а не установленный инцидент. Также нельзя позволять атакующему заранее зарегистрировать чужую почту и сохранить свою сессию после её подтверждения владельцем ящика.

Для новых пользователей предлагается ограниченный onboarding до подтверждения почты, затем отдельный обычный вход. Для уже существующих — уведомление внутри аккаунта и контролируемая привязка, без массового подтверждения, удаления данных или внезапной блокировки этим изменением. Исправление ошибочного адреса — отдельное повторно аутентифицированное действие с подтверждением нового адреса, не параметр публичного reset-запроса. Пока эта миграционная политика не согласована и не проверена, R4 не закрывается.

## 3. Данные и одноразовые подтверждения

Планируемые названия ниже — контракт для реализации, не существующие таблицы/API.

- `account_recovery_bindings`: user ID, точный подтверждённый email, время и версия доказательства. Хранится отдельно от публичного профиля; не экспортируется общей выдачей User. Legacy-флаг может отражать результат, но не заменяет binding.
- `auth_challenges`: ID, user ID, назначение `email_verify` или `password_reset`, digest токена, адрес/версия binding на момент выдачи, версия реквизитов, даты создания/истечения/использования/отзыва. Для привязки также фиксируется инициирующая сессия, чтобы её отзыв или ротация отменяли незавершённую привязку.
- Версия реквизитов аккаунта меняется при изменении пароля/reset/адреса; не используем общий `updatedAt`, который меняется и при переключении контекста. Добавление поля не должно менять существующие пароли и сессии.

Токен — 32 случайных байта из криптографического генератора; digest разделён по назначению. Session token, verification token и reset token не взаимозаменяемы. В таблице challenges нет исходного токена; не возвращаем его в публичном JSON. Для минимальной реализации выбираем непрозрачный токен, а не самостоятельный JWT со вторым механизмом отзыва.

Начальные проектные значения: **30 минут для reset, 24 часа для привязки email**, не более одного действующего challenge каждого назначения на аккаунт. Это наши исходные параметры, не обязательные числа из внешнего стандарта; перед выпуском их проверяем на реальной доставке. После разрешённой повторной выдачи предыдущий challenge того же назначения отзывается. Отказ из-за cooldown не уничтожает ещё рабочую ссылку. Повтор транспортной доставки использует тот же challenge и не продлевает срок.

`GET`/предпросмотр письма не меняет пароль, не подтверждает email и не расходует token. Погашение происходит только явным `POST` после проверки всех условий. Неудачная валидация нового пароля не расходует token. Для одной ссылки допустим ровно один успешный commit даже при двух одновременных запросах.

Сохраняем действующее сравнение email в проекте; не удаляем точки/plus-суффиксы, не объединяем аккаунты по похожим адресам. До расширения поддержки регистра и международных адресов нужны отдельные тесты коллизий и миграции. Любой путь изменения email должен отзывать старый binding и challenges; обычный профильный update не должен принимать эти защищённые поля от клиента.

## 4. Два разных пользовательских пути

### Привязка канала

В настройках человек подтверждает текущий пароль и получает письмо на сохранённый email. Ссылка открывает пояснение, а не выполняет действие. Подтверждение требует того же аккаунта, действующей привязанной сессии, актуального пароля и token. При смене аккаунта, отзыве/ротации сессии, изменении адреса или реквизитов выдаём отказ без привязки. После первой успешной привязки завершаем прежние сессии и просим войти заново; это отдельное правило будущей привязки, не изменение BETA-005b/c этим документом.

### Забытый пароль

Человек вводит email, получает нейтральное подтверждение запроса, открывает письмо, вводит новый пароль дважды и после успеха входит обычным способом. Старый пароль не требуется только потому, что предъявлено другое заранее установленное доказательство. Сессия полного доступа автоматически не создаётся.

Внутри одной write-транзакции: блокировка пользователя, повторная проверка binding/версии/назначения/digest/срока, расходование challenge, изменение хеша, увеличение версии реквизитов, отзыв остальных challenges и **всех** старых сессий, аудит и постановка уведомления о смене пароля в надёжную отправку. Ошибка любой DB-записи откатывает всё. Хеширование выполняется вне короткой блокировки; актуальность снимка проверяется повторно внутри неё. Никаких паролей или токенов в аудите.

Порядок блокировок согласовываем с текущими login/password/manual-revocation: сначала user, затем связанные записи в фиксированном порядке. Истечение проверяется заново после ожидания, не по старому времени начала запроса. Успешная обычная смена пароля тоже должна инвалидировать ранее выданные reset-ссылки. Запоздавший login со старым снимком реквизитов не создаёт новую сессию после reset.

При потере ответа после commit результат для браузера остаётся неизвестным: не обещаем откат, не повторяем чувствительную операцию автоматически. Предлагаем обычный вход с новым паролем либо новый запрос восстановления. Письмо-уведомление после reset не содержит пароль; сбой его фактической доставки не возвращает прежний пароль и не оживляет старый token.

## 5. Доставка: отдельная проверяемая часть

Рабочее техническое предложение — небольшой **PostgreSQL outbox и SMTP-адаптер в существующем коде**, без Redis, внешнего брокера или отдельной платформы авторизации. Новые компоненты вводятся отдельной подзадачей, не этим документом и не вместе с первой таблицей challenges.

Чтобы SMTP-задержка не выдавала существование аккаунта, публичный запрос сначала ставит одинаковую ограниченную задачу для любого синтаксически допустимого адреса, без синхронного SMTP и без различающего внешнего результата поиска. Проверка права на recovery и выдача challenge выполняются обработчиком. Очередь имеет ограничение размера, срока хранения и повторов, устойчивые ограничения по адресу и контролируемый запуск/остановку. Временной профиль ответа всё равно нужно измерять; одно слово «очередь» не доказывает отсутствие утечек.

Challenge и задание письма создаются согласованно в БД; SMTP выполняется вне DB-транзакции. Outbox не хранит открытый токен: чувствительный payload, необходимый для повторной отправки, шифруется с аутентификацией отдельным версионированным ключом вне БД, не захардкоженным и не автоматически заменённым на AUTH_SECRET. Таким образом, digest-only относится к проверочной таблице, а зашифрованный payload доставки — отдельный явно учтённый секрет. Отсутствие ключа запрещает включение, а не переводит payload в plaintext. После успеха, отмены или истечения payload удаляется по ограниченной политике хранения; резервные копии и смена ключа включаются в эксплуатационную проверку.

При падении между SMTP-ответом и записью результата возможна повторная доставка того же письма, не второе изменение аккаунта. Перед отправкой и повтором проверяем актуальность challenge; не рассылаем заведомо истёкшие/отозванные ссылки. Уже отправленное письмо нельзя отозвать из ящика — сервер обязан отказать по недействительной ссылке. Не обещаем exactly-once доставку. Состояния «записано в очередь», «принято SMTP» и «получено пользователем» различаются.

Сначала адаптер проверяется на изолированном SMTP-приёмнике в Docker, который не пересылает письма в интернет. Режим log не печатает пароли, token и полную ссылку и не считается доказательством доставки. Для production понадобятся проверка TLS/сертификата SMTP без небезопасного fallback, согласованный sender/домен, реальные тестовые ящики и обработка отказов. Провайдер, секреты, DNS, биллинг и production Compose этим шагом не меняются.

## 6. HTTP, ошибки и защита от злоупотреблений

Предлагаемые endpoints: authenticated `email-verification/request` и `email-verification/confirm`; public `password-reset/request` и `password-reset/confirm` под `/api/auth`. Их пока нет; новые ссылки интерфейса не показываем как работающие до реализации.

Для допустимого reset request — одинаковый HTTP 202, текст, структура и заголовки при существующем, неизвестном, неподтверждённом или неподдержанном аккаунте: «Если для этого адреса доступно восстановление, вы получите письмо с дальнейшими действиями». Никаких признаков найденного пользователя, masked email, счётчиков сессий или статуса доставки. Глобально выключенная функция/недоступность очереди отвечает одинаковым 503 независимо от адреса; публичный endpoint не притворяется рабочим. Ошибка формата 400 и IP-лимит 429 не зависят от наличия аккаунта. Адресный cooldown применяется одинаково и не возвращает отличающийся ответ.

Начальная гипотеза лимитов: 5 запросов за 15 минут на IP, не чаще одного письма в минуту и трёх в час на нормализованный адрес, отдельный лимит попыток confirm. Значения нужно измерить с учётом общих IP; адресные ключи псевдонимизируются, сравнение не зависит от наличия user. Ограничения отправки сохраняются при перезапуске. Требуются верхние границы размера запроса/очереди и срока жизни задач. Запрос восстановления никогда не блокирует обычный аккаунт и не завершает его сессии.

Для reset/verify выбираем ссылку с token во фрагменте (`#token=...`), чтобы начальный запрос к прокси не содержал секрет. Страница читает его в память, убирает фрагмент из адресной строки и отправляет только в body подтверждения по HTTPS. После перезагрузки без token нужно заново открыть письмо, а не хранить token в localStorage или логах. Базовый URL берётся только из проверенной конфигурации, не из Host/X-Forwarded-Host и не из пользовательского redirect.

Страницы/ответы чувствительных операций: no-store, Referrer-Policy no-referrer, отсутствие сторонних ресурсов/аналитики, исключение секретных полей из журналов, ошибок, трассировок, screenshots и CI artifacts. Проверяем реальные прокси-логи, не только console приложения. Cookie-аутентифицированная привязка требует CSRF-защиты и проверки origin; SameSite не объявляется единственной защитой. Ссылки и token не меняют аккаунт через GET.

Невалидный/истёкший/использованный/чужого назначения token даёт одинаковую понятную ошибку с предложением запросить новую ссылку. Формы используют общую парольную политику, подписи, автозаполнение и RU/EN. Этот проект не утверждает, что существующие 8–128 символов уже прошли полный password-policy review. Также нейтральный reset не устраняет существующие раскрытия занятости email/username при регистрации: это остаётся отдельной строкой общего security review.

## 7. Небольшие этапы и критерии приёмки

Все строки, кроме D0, **не выполнены**. Уровень доказательств указан заранее, не как результат.

|---|---|---|
| D0 / этот шаг | Инвентаризация, проект правил и план | Ссылки на исходный SHA; факты отделены от предложений; R4 не закрыт. |
| D1 / следующий | Модель binding/challenge/версии и атомарное одноразовое погашение на DB-уровне | Миграция на новой БД без авто-подтверждения старых user; разные назначения; неверный/истёкший/использованный token; конкурентное погашение; откат состояния и аудита. Без SMTP, HTTP reset, UI и изменения текущих паролей. |

| D3 | Аутентифицированная привязка сохранённого email | Сессия + текущий пароль + письмо; разные аккаунты; stale email/сессия/версия; GET не подтверждает; CSRF; отзыв прежних сессий; legacy-флаг не достаточен. Политику активации согласовать до включения. |
| D4 | Реальные reset request/confirm и формы | Равные внешние ответы и измерение времени; единый DB commit; отзыв всех сессий/challenges; обычный вход новым паролем; старые cookie/пароль не работают; смена пароля инвалидирует ссылки; нет утечки через URL/log/metadata. |
| D5 | Сквозная приёмка и подготовка включения | Chromium/HTTP + настоящая БД + закрытый SMTP-приёмник; mail preview без расходования; ошибки/клавиатура/узкий экран/RU/EN; затем отдельно реальные sender/ящики/доставка, ограничения эксплуатации и явное разрешение. |

D1 не внедряет полное восстановление под видом одной миграции. Сначала репозиторные инварианты, затем отдельное подключение к user-facing операциям. Не вводим тестовые backdoor-endpoints или массовый seed, не меняем рабочие базы. Прежние account/password/manual-revocation и Docker-проверки сохраняются.

Обязательные негативные сценарии D3–D5: чужая сессия/адрес/назначение, подмена userId, токен до смены пароля или адреса, истечение во время ожидания user lock, два одновременных reset, reset против login/password/manual revoke, replay старых cookie, ошибка аудита/outbox, потеря HTTP-ответа после commit. DB-откат и сетевую неопределённость описываем отдельно.

## 8. Что необходимо решить перед включением

Ответственный за выпуск отдельно принимает правила активации новых пользователей и перехода существующих, поддержку привилегированных/MFA-аккаунтов и границы случаев без доступа к почте. До этого автоматическое подтверждение старых записей, новая блокировка входа или ручной административный сброс запрещены. Технические числовые значения и способ доставки — рабочая рекомендация для реализации, а не уже введённая политика эксплуатации.

R4 закрывается только после действующего проверенного процесса, понятных пользователю ограничений и приёмки выбранной среды. Наличие этого документа, зелёный старый CI, успешный SMTP handshake или запись в тестовом ящике по отдельности этого не доказывают. Релизные решения остаются в RELEASE-READINESS, а не в новом параллельном roadmap.

## 9. Основания решения

Первичные источники сверены 2026-09-24; они не являются проверкой нашего кода:

- [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html): одноразовые ограниченные по времени доказательства, нейтральный запрос, обычный вход после reset и уведомление.
- [OWASP Email Validation and Verification](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html): подтверждение адреса, явная политика сравнения, отсутствие секретов в журналах.
- [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html): повторная аутентификация чувствительных изменений и различение подтверждения личности/сессии.
- [OWASP WSTG, password change/reset](https://owasp.github.io/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/04-Authentication/09-Weak_Password_Change_or_Reset_Functionalities): проверка стойкости reset, назначения/срока token, утечек и обхода факторов.
- [Drizzle transactions](https://orm.drizzle.team/docs/transactions) и [PostgreSQL 18 locking](https://www.postgresql.org/docs/18/explicit-locking.html): механизмы для атомарности и согласованного порядка операций, которые нужно проверить на нашей реализации.

Запись D0: новые runtime-тесты восстановления не выполнялись, поскольку реализация этим изменением не добавляется. Исходная Verify-проверка `03465c6` [успешна](https://github.com/acc-holo-dev/mta-nexus-site/actions/runs/35950704042/job/107478412778); она относится к существующему приложению, не к будущему recovery. Следующий шаг — D1.
