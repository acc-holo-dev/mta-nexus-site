# PROBLEMS — реестр открытых проблем MTA NEXUS

Единственный реестр проблем проекта. Обновлён: 2026-10-03 (после полного
статического аудита и этапа целостности ресурсов; новый браузерный прогон не выполнен).

Правила реестра:

- каждая проблема имеет приоритет, описание, доказательство и следующий шаг;
- закрытая проблема удаляется из реестра в том же коммите, который её закрыл
  (история — в commit messages и CI evidence);
- проблемы не дублируются в других документах; OPERATIONS ссылается сюда.

Приоритеты: `P0` — блокер релиза, `P1` — существенная проблема качества,
`P2` — известное ограничение, требующее работы, `P3` — улучшение/гигиена.

---

## P0 — блокеры релиза

### P0-1. GitHub Actions не выполняет jobs

- **Симптом:** workflow-запуски создают jobs, но jobs содержат `steps: []` и
  завершаются до первого шага (`runner_id: 0`, пустое имя раннера). Пример:
  [run 36530389835](https://github.com/acc-holo-dev/mta-nexus-site/actions/runs/36530389835)
  на `6b32ce0`: все пять jobs завершились без шагов; подтверждено повторно
  2026-09-29. Локальные lint/typecheck/build прошли, но это не исправляет CI.
- **Последствие:** `main` не проходит CI-гейты (lint/typecheck/test/build),
  поэтому дрейфы кода и тестов накапливаются незамеченными — в сентябре это
  уже привело к 23 падающим тестам на `main`.
- **Владелец:** владелец репозитория (настройки GitHub недоступны из кода).
- **Следующий шаг:**
  1. проверить Actions policy, доступность hosted-раннеров, billing/quota и
     ограничения workflow-уровня в настройках репозитория/организации;
  2. восстановить исполнение jobs;
  3. перезапустить CI на точном SHA текущего `main`;
  4. включить обязательные status checks для push в `main`;
  5. проверить зависшие Dependabot PR (ветка старого PR удалена при чистке
     веток 2026-09-29 — пересоздать PR или обновить версии локально).

## P1 — существенные проблемы

### P1-1. Lint-предупреждения и неполная интеграционная проверка

2026-09-29 восстановлен полный снимок main `1ae7f75`: все 547 файлов
сверены по Git blob SHA. После обновления профилей организаций выполнен полный
`pnpm lint` (Biome 2.5.14): **515 файлов, 0 ошибок, 140 предупреждений, 37 info**.

Проверки в окружении Node 26.10.0 / pnpm 12.4.2:

- зависимости установлены через `pnpm install --frozen-lockfile`;
- полный `pnpm typecheck` прошёл;
- production `pnpm build` прошёл на предыдущем этапе; повторная сборка
  2026-10-03 блокируется окружением: Turbopack не может открыть служебный
  локальный порт (`Operation not permitted`), включая повтор с расширенными
  разрешениями; сборка текущего изменения не подтверждена;
- `test:resource-integrity`: 127 тестов в 15 файлах;
- `test:scanner`: 119 тестов в 17 файлах;
- `test:catalog`: 85 тестов в 19 файлах;
- `test:resource`: 16 тестов в 6 файлах;
- контракты доступа, private-cache, upload и mainline: 26 тестов в 5 файлах.

Группы частично пересекаются; складывать их как число уникальных тестов нельзя.
Полный `pnpm test`, новые PostgreSQL integration-тесты и браузерные сценарии
не запускались: в окружении отсутствуют PostgreSQL и Docker. Моки seed проверяют
откат и сохранение данных на уровне логики, а не реальные SQL-блокировки.
Сборка не доказывает работу БД, SMTP, ClamAV или production HTTP-сценариев.

**Следующий шаг:** выполнить `pnpm test:isolated` и браузерный прогон на
Compose-стеке, затем восстановить CI на точном SHA. Продолжать сокращать
оставшиеся lint-предупреждения по смыслу.

### P1-2. Заголовки детальных страниц (a11y/SEO)

Проверка исходников 2026-09-30 подтвердила `<h1>` на страницах ресурса,
сервера, статьи, пользователя, разработчика и организации. Рендер профиля
разработчика проверен на RU/EN: один h1. Добавлены title/description/canonical
для профилей разработчика и организации; неподходящие роли не получают
индексируемый профиль разработчика. Отсутствующие пользователи и организации
получают локализованный заголовок и явный noindex/nofollow в метаданных.
Канонические адреса строятся из сохранённых идентификаторов профилей; описание
организации ограничено 155 символами с локализованной заменой пустого текста.

Попутно исправлена выборка работ разработчика: вместо фильтрации первых 100
ресурсов всего каталога выполняется существующий запрос по автору с условиями
публичности, бесплатности и безопасной опубликованной сборки.

Профили разработчика, пользователя и организации показывают по 24 ресурса на странице. Общий
счётчик и выдача используют одинаковый фильтр автора или организации, публичности и безопасной
сборки. Некорректные параметры нормализуются, устаревшая ссылка за пределами
портфолио показывает последнюю доступную страницу. Серверы пользователя
выводятся по 12 записей с отдельным общим счётчиком. Параметры `page` и
`serverPage` сохраняются независимо при переходах между страницами.
Статьи организации выводятся по 12 записей: типы публикаций отбираются в SQL
до count/limit, общий счётчик не ограничен первыми 100 записями. Параметры `page`
и `articlePage` сохраняются независимо; устаревшие ссылки ограничиваются
последней доступной страницей каждого раздела.

- **Проверено:** тесты рендера, метаданных, доступа, SQL-условий и границ пагинации;
  типизация и lint; production-сборка текущего изменения заблокирована
  ограничением окружения (см. P1-1).
- **Следующий шаг:** проверить реальные страницы и скриншоты на двух языках,
  включая несколько страниц большого портфолио. Замерить count/offset запросы
  на PostgreSQL; при очень больших объёмах рассмотреть пагинацию по курсору.


## P2 — известные ограничения

### P2-1. Внешние ресурсы недоступны из сети владельца

`master.multitheftauto.com` (master-list) и `images.unsplash.com` (превью seed-
данных) не отвечают даже с хоста — похоже на региональную блокировку сети.
Приложение деградирует честно («directory temporarily unavailable», «Нет
превью»), но каталог выглядит пустым, а live-серверы не отображаются.

- **Следующий шаг:** подтвердить причину (региональная блокировка vs downtime);
  рассмотреть self-hosted превью (загрузка скриншотов в приватное storage) и
  прокси/зеркало для master-list в production-инфраструктуре; для dev —
  документировать ожидаемую деградацию.

### P2-2. Dev-стек хрупок к hostname (Next dev origin-checks)

Доступ к dev-приложению через не-localhost hostname (например
`nexus-local-app-1:3000` из соседнего контейнера или по IP) ломает HMR-
соединение и гидрацию целиком: React-обработчики не подключаются, формы
сабмитятся нативным GET, auth-check не выполняется. Через `localhost:3000`
всё работает. Проверено живым браузером 2026-09-29 (Chromium и Firefox).

- **Изменение:** `0d9b7c5` разрешает точный hostname контейнера в
  `next.config.mjs`; README объясняет доступ из Compose-сети.
- **Следующий шаг:** пересобрать dev-образ, проверить гидрацию и отправку форм
  через `localhost:3000` и `nexus-local-app-1:3000` в браузере. Доступ по
  произвольному IP требует отдельного явного разрешения и проверки.

### P2-3. Seed и скачивание: остаётся интеграционная приёмка

Реализованы настоящие ZIP для inventory и drift, транзакционный повторяемый
seed, проверка занятых ID/slug, сохранение пользовательских правок и явный
`db:seed:repair` для size/hash известных демосборок. Чужие файлы не заменяются;
модерационные статусы не сбрасываются. Изменённая версия/статус продукта
блокирует повторное добавление отсутствующей демосборки.

- **Проверено:** файловые и HTTP-тесты, логика транзакций с моками, типизация
  и сборка. Публичное и модераторское скачивание отклоняют известное
  несовпадение размера/хеша до аудита; исчезнувший файл возвращает 404.
- **Проверено 2026-09-30:** локальный provider хеширует открытый файл перед
  выдачей. Настоящее повреждение того же размера отклоняется обоими HTTP-
  маршрутами до аудита. Запись файлов атомарна; повторный ключ и проигравшая
  конкурентная запись не перезаписывают опубликованные байты.
- **Ограничение:** внешняя запись в тот же inode после проверки остаётся
  возможной; это не неизменяемый снимок файловой системы. Хеширование добавляет
  полное чтение с диска перед ответом — нужен нагрузочный замер. Чужие
  placeholder-файлы и временные файлы после аварийного завершения процесса
  требуют ручного разбора.
- **Проверено дополнительно:** длинные/Unicode имена архивов не входят в ключ
  хранения; идентификатор владельца проверяется до записи файлов.
- **Проверено дополнительно:** отмена запроса прекращает подготовку архива
  между блоками чтения и закрывает поток. Тесты покрывают отмену до открытия,
  во время хеширования, до/во время аудита и очистку обработчика отмены.
  Обрыв настоящего сетевого соединения в запущенном Next.js ещё не проверен.
- **UI скачивания:** ошибки теперь остаются на странице ресурса с RU/EN
  сообщениями, прогрессом и отменой. Тесты клиента и серверного рендера прошли;
  Playwright-сценарий обновлён для ошибки 409 и повторного скачивания, но не
  запускался. В браузере проверить сохранение файла, отмену и расход памяти
  на 64 МиБ (Blob требует дополнительных аллокаций).
- **Следующий шаг:** на PostgreSQL 18 выполнить миграции, seed дважды,
  адресный repair и оба claim/download-сценария; проверить сохранность
  пользовательских правок и поведение реальных конкурентных транзакций.
  Новые integration-тесты подготовлены, но здесь не запускались.

### P2-4. Приёмка ограничения `products.type` на PostgreSQL

Добавлены единый реестр девяти типов, согласованные UI/валидация/каталог и
миграция `0024_product_type_invariant` с CHECK. Только известный исторический
алиас `tool` преобразуется в `plugin`; неизвестные значения останавливают
миграцию. Форма публикации теперь также предлагает API, набор и сервис.

- **Проверено:** соответствие реестра SQL-ограничению, входной валидации и
  русским/английским вариантам формы; типизация и production-сборка.
- **Следующий шаг:** проверить распределение существующих типов, применить
  миграцию в изолированном PostgreSQL 18 и запустить
  `pnpm test:resource-integrity:integration`. До этого ограничение в живой
  БД не считать установленным или проверенным.

### P2-5. Тестовая инфраструктура: хрупкости и производительность

- root `tests/` импортируют `next/server`, `drizzle-orm` — работает через
  root devDependencies (`ea5235c`); долгосрочно тесты стоит перенести в
  соответствующие пакеты воркспейса;
- surface-тесты сверяют точные строки исходников — ломаются при
  переформатировании; при правках предпочитать regex/поведенческие проверки;
- `fileParallelism: false` в `vitest.config.ts` (сделано ради детерминизма
  account-mail очередей) увеличил полный прогон до ~65s; при желании вернуть
  скорость — вынести mail-сьюиты в отдельный vitest-проект со своей БД;
- policy-тест документов (`tests/mainline-repository-policy.test.ts`) —
  источник правды по составу документации.

### P2-6. Хост-тулинг не соответствует engines

Хост: Node 22.23.2 / pnpm 12.4.1; проект требует Node ≥ 26 / pnpm 12.4.2.
Хост-скрипты `pnpm dev:docker:*`, `pnpm test:isolated` работают через Docker,
но host-side `pnpm check` без контейнера невозможен. pnpm-автоустановка
зависимостей при host-run создаёт лишний `node_modules` на хосте — установка
предотвращена (`verifyDepsBeforeRun: warn`).

- **Следующий шаг:** обновить хост (`nvm install 26`, corepack pnpm@12.4.2)
  либо держать разработку строго в Docker-пути.

## P3 — гигиена и улучшения

- **Админка EN-only** — словарь не покрывает `/admin`; известное ограничение
  закрытой беты (README документирует область словаря).
- **Hydration mismatch warning** от theme-инициализации (inline script читает
  `localStorage` до гидрации) — кандидат на `suppressHydrationWarning` у
  корневого `<html>`/theme-провайдера; поведение корректно.
- **Dev-БД загрязнена тестовыми данными** (~1600 пользователей, `*_mum*`
  артефакты integration-тестов) — ожидаемо для dev; для чистых прогонов
  использовать `pnpm test:isolated`; при необходимости пересоздать том
  `nexus-local_pgdata` и накатить `pnpm db:seed`.
- **Проверять «живость» сайта браузером регулярно** — скрипты живого тура
  сохранены вне репозитория (`~/nexus-ux-audit/`), запускаются контейнерным
  Chromium против `localhost:3000` (установить: `apk add chromium` в dev-контейнер,
  `npm i playwright-core` в `/tmp` контейнера).
