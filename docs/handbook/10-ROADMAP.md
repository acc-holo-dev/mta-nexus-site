# План разработки

## Как выбирать работу

Берите одну законченную задачу с понятным пользовательским результатом. Сначала устраните блокирующие дефекты и риски данных, затем развивайте связанные функции. Владелец разрешает выбирать технический порядок самостоятельно; утверждённые цели находятся в [реестре решений](13-DECISION-REGISTER.md). Наличие цели не означает, что функция уже работает.

## Рабочая очередь

Каждая строка — незакрытая задача с результатом и приёмкой. Номер обозначает зависимость, а не отдельный документ или ветку. 18 закрыт для основных путей; 19 остаётся CI disposable-volume residual; 20 даёт checkable harness без live/deploy. Независимые участки можно брать параллельно. Проверка области может подтвердить, что исправления не нужны: тогда достаточно воспроизводимого результата, без искусственного изменения кода.

| № | Цель и граница работы | Зависит от | Критерий готовности |
|---|---|---|---|
| 19 | Повторить обновление БД и парное восстановление данных/файлов. | — | Контракт mount-топологии `compose.production.yaml` закреплён тестом; CI-green (#126) и library/history `@nexus/ui` (#127) на tip. Residual: зелёный full_acceptance + `backup-restore-evidence.json` на текущем tip SHA для кандидата 20. Рабочие/production-данные не изменены. |
| 20 | Подготовить проверяемый кандидат открытой бесплатной беты. | 06–09, 13–19 | Harness `pnpm beta:candidate` готов: exact-SHA приёмка (CI full_acceptance + jobResults, TLS/runtime, mail, storage/scanner, browsers, DB upgrade, backup/restore) с именованными блокерами; `openBetaLive`/`productionAuthorized` никогда не true. Checkable только после PASS-артефактов на текущем tip; blocked-by 19 CI evidence на tip + owner deploy/observability/legal. Marketplace/DRM вне scope. Развёртывание требует отдельного разрешения. |

У каждой параллельной задачи один владелец и непересекающиеся файлы. Изменения общих helpers, CI и документации собирает основной агент; PostgreSQL-тесты исполнителей используют разные одноразовые БД. Полные проверки и тяжёлая сборка выполняются один раз после интеграции. Завершённые задачи удаляются из очереди после включения в `main`, номера оставшихся сохраняются; доказательства и история остаются в PR и Git.

Подтверждённые незакрытые дефекты ведите только в [PROBLEMS.md](../PROBLEMS.md), со ссылкой на соответствующую цель при необходимости. Не удаляйте тесты и ограничения ради ускорения приёмки. Никакая задача этой очереди не включает реальные платежи или production-развёртывание без отдельного решения владельца.

## Поздние и необязательные возможности

GitHub import/release sync, webhooks, API для authenticated partners/Pro и расширенная аналитика — возможные последующие задачи. Артефакты GitHub проходят общий safety pipeline. Внешний API и отдельная публичная Status Page не блокируют запуск; внутренняя наблюдаемость обязательна.

Масштабирование, Redis, распределённые очереди и выделение сервисов обосновываются измеренными ограничениями монолита. Перед добавлением инфраструктуры определите проблему, стоимость сопровождения, проверку и способ восстановления.

## Завершение задачи

Код реализует заявленное поведение, серверные права и ошибки проверены, соответствующие тесты проходят. Изменения схемы сопровождаются новой миграцией; документация отражает действующие правила. Коммит содержит одну логическую задачу. Итог называет результат, выполненные проверки и оставшиеся ограничения. Релиз отдельно требует точного SHA, целевой приёмки и разрешения владельца.
