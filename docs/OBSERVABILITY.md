# Observability baseline

OBS-001 introduces a dependency-free structured logging baseline for the highest-risk API routes. It is intentionally smaller than a full tracing platform.

## Correlation contract

Each migrated API handler creates a server-generated request context:

- `requestId`
- HTTP method
- pathname only

Responses from the migrated handlers include:

```text
X-Request-Id: <server-generated id>
```

The request ID is generated by the application. Client-provided request IDs are not trusted or reused in this first slice.

The pathname excludes the query string so reset proofs, search terms, or future query credentials cannot be copied into logs accidentally.

## Structured event format

Operational events are emitted as one-line JSON. Example shape:

```json
{
  "timestamp": "2026-09-25T00:00:00.000Z",
  "level": "error",
  "event": "directory.fetch_failed",
  "requestId": "4c3c...",
  "method": "GET",
  "path": "/api/servers/directory",
  "status": 503,
  "error": {
    "name": "Error",
    "code": "ECONNRESET"
  }
}
```

Unknown errors intentionally do not serialize the raw error message or stack. Error messages from database drivers, SMTP libraries, filesystem calls, or upstream clients can contain infrastructure details and must not become logs by default.

Flat custom fields are allowed, but keys resembling authorization, cookies, tokens, secrets, passwords, email addresses, IP addresses, headers, body, query, or URL fields are dropped. Core identity fields such as `requestId`, `event`, `method`, `path`, `status`, and `error` cannot be overridden through custom fields.

## Initial route coverage

The first slice covers:

- login
- password reset request/confirm
- resource build upload
- moderation report list/submit
- official MTA directory
- health/database reachability

This is not yet global request middleware and does not claim that every route is correlated. Additional routes should migrate incrementally after this contract is accepted.

## Privacy and security boundary

Do not add the following to structured log fields:

- request/response bodies
- session tokens
- password/reset/verification proofs
- cookies or authorization headers
- email addresses
- client IP addresses
- uploaded filenames or file contents
- database URLs or SMTP credentials

User-visible error responses may contain the request ID header for support correlation, but logs must remain useful without recording account-specific secrets.

## Future integration

Sentry/OpenTelemetry may consume or complement this structure later. OBS-001 deliberately adds no vendor SDK and no network exporter. The JSON event names and request correlation boundary should stabilize first.
